# Atelier n°7 — Datacenter, vCenter et migrations

Durée source : **deux à trois heures**. Objectifs : déployer une appliance vCenter,
gérer un datacenter et utiliser vMotion/Storage vMotion. Prérequis : les deux ESXi,
leurs réseaux et stockage des ateliers 3 à 5, la VM Windows Server 2019 d’atelier 1
et les deux VM invitées d’atelier 6.

Tous les paramètres propres à la salle sont neutralisés. Les adresses, masques,
passerelle, résolveur et noms doivent rester cohérents dans le laboratoire ; les
variantes de notation des PDF ne sont pas résolues par des valeurs inventées.

## 1. Préparer DNS

Sur le serveur Windows de laboratoire :

1. Ajouter une seconde carte réseau avec une IPv4 statique dans le réseau /16
   prévu par le scénario ; lui indiquer le serveur DNS du laboratoire.
2. Installer le rôle DNS. La solution ajoute aussi le suffixe DNS principal au serveur.
3. Créer une zone de laboratoire `<domaine-de-laboratoire>` et les enregistrements
   A des deux ESXi et de vCenter, vers leurs adresses respectives.

Sur chacun des deux ESXi, ouvrir la configuration locale avec F2, renseigner le
résolveur DNS et le suffixe du laboratoire, puis confirmer les modifications.
Ces changements affectent l’accès de gestion et sont limités à cet environnement.

## 2. Déployer l’appliance

1. Obtenir séparément l’appliance vCenter `<appliance-de-laboratoire>.ova`.
   Le partage interne mentionné dans les sources n’est pas republié.
2. Ouvrir cette appliance avec Workstation et choisir le mode historique
   **Tiny server with embedded PSC** indiqué par le document.
3. Fournir l’adresse statique, le préfixe /16, la passerelle, le serveur DNS et
   le nom FQDN cohérents du laboratoire. Attendre la fin du déploiement.
4. Définir le secret d’administration en tenant compte du clavier QWERTY signalé.
   L’exemple de secret du PDF est exclu de cette adaptation.

Les binaires et licences ne sont pas joints aux PDF. Le mode de déploiement décrit
est celui de la source historique, sans recommandation de version actuelle.

## 3. Configurer VCSA puis le datacenter

Depuis un système graphique utilisant le DNS préparé, ouvrir le FQDN de
l’appliance en HTTPS sur le port **5480**. Suivre Configurer et créer le domaine
SSO indiqué par l’assistant historique. Les comptes et valeurs effectifs sont
des paramètres de laboratoire. La solution demande de laisser l’assistant finir ;
elle propose de rafraîchir et recommencer s’il boucle, sans en documenter la cause.

Accéder ensuite à vSphere en HTTPS sur **443**, s’authentifier avec le compte SSO
préparé et créer `<datacenter-de-laboratoire>`. Ajouter les deux ESXi avec leurs
propres identifiants d’administration, distincts de ceux de vCenter. Les alertes
de certificat montrées sont à examiner dans leur contexte ; elles ne constituent
pas une autorisation générale d’acceptation automatique.

## 4. Migrations : deux scénarios à distinguer

!!! warning "NEEDS_REVIEW — énoncé et solution différents"

    L’énoncé vise une VM non définie dans les prérequis, demande son stockage vers
    la banque iSCSI puis son déplacement vers le premier hôte. La solution utilise
    les deux VM préparées : calcul de la seconde vers le premier hôte, puis fichiers
    de la première du stockage local vers NFS. Faire arbitrer le scénario à exécuter ;
    aucun nom ou chemin manquant n’est fabriqué.

**Demande de l’énoncé :** relever l’espace de la banque iSCSI, déplacer le stockage
de la VM désignée sans l’arrêter, observer l’effet sur la banque, puis déplacer
la VM vers le premier ESXi et contrôler le déroulement.

**Parcours de la solution :** maintenir la seconde VM démarrée et migrer ses seules
ressources de calcul vers le premier ESXi. Maintenir la première VM démarrée et
migrer ses seuls fichiers du datastore local vers le datastore NFS. Contrôler
l’impact sur les banques et le fonctionnement des VM. Les détails observables
sont présentés dans la correction, sans fusionner les deux parcours.
